Product Overview

What is EventX?

EventX is a full-stack web application designed to manage every aspect of large-scale academic and cultural festivals. It replaces spreadsheets, paper forms, and manual coordination with a unified, role-based digital platform — from participant registration to real-time result publishing.

The platform is purpose-built for the ISRA Vatanappally Life Festival ("Rendezvous'26"), supporting 500+ participants across 20+ event categories with multiple competition teams.

Architecture Summary

EventX is a React SPA (Single Page Application) using Vite as the build tool, Supabase as the backend (PostgreSQL + Auth + Storage), and Tailwind CSS for styling. The app is deployed on Vercel with SPA catch-all routing.

All server-side logic is handled by PostgreSQL functions (RPCs) — there are no Edge Functions or separate API servers. Real-time subscriptions are not used; the app operates on a pull/refresh model.

Authentication & Security

Supabase Client Configuration

Three separate Supabase client instances are created in src/supabase/client.js, all sharing the same URL and anon key but with different storageKey values to prevent session collisions:

ClientVariablestorageKeyPurpose
MainsupabaseDefault (sb-*-auth-token)Admin auth, all data queries
JudgejudgeClientartfest-judge-authJudge authentication (isolated session)
VerifyverifyJudgeClientartfest-verify-authRe-verification flow (persistSession: false)

Role System

Roles are stored in auth.users.raw_app_meta_data and carried in the JWT as app_metadata.role. Two SQL helper functions are defined:

CREATE OR REPLACE FUNCTION public.is_admin() RETURNS boolean AS $$
  SELECT COALESCE(auth.jwt() -> 'app_metadata' ->> 'role', '') = 'admin';
$$;

CREATE OR REPLACE FUNCTION public.is_judge() RETURNS boolean AS $$
  SELECT COALESCE(auth.jwt() -> 'app_metadata' ->> 'role', '') = 'judge';
$$;

Admin Authentication Flow

  1. User navigates to /admin/login
  2. AdminSessionRedirect checks if session already exists → redirects to /admin if so
  3. Admin enters email + password
  4. supabase.auth.signInWithPassword({ email, password }) is called
  5. On success, JWT is stored with app_metadata.role = "admin"
  6. Navigate to /admin with replace: true (no back-stack entry for login)
  7. ProtectedRoute on all /admin/* routes verifies session exists

Student Authentication Flow

  1. Student navigates to /student/login
  2. Enters chest number and password
  3. getStudentByCredentials(chestNo, password) queries the students table
  4. Checks student_credentials table for password match
  5. Falls back to common password israfest2026 if no per-student credential exists
  6. Checks sessionActive in DB — rejects with 'already_logged_in_elsewhere' if true
  7. Creates session: stores token in localStorage (student_session_<id>) and DB (sessionActive=true, sessionToken, sessionExpiresAt)
  8. Session expires after 8 hours (SESSION_EXPIRY_MS = 8 * 60 * 60 * 1000)
  9. Student ID stored in localStorage.setItem('student_id', id)
Note: Students authenticate as the anon role in Supabase Auth. Their writes to the students table are gated by RLS policies requiring auth.role() = 'authenticated', so students cannot write directly via PostgREST.

Judge Authentication Flow

  1. Judge navigates to /judges/login
  2. Any existing judge session is cleared: judgeClient.auth.signOut()
  3. Enters email + password
  4. judgeClient.auth.signInWithPassword({ email, password }) is called
  5. After sign-in, checks data.user.app_metadata.role
  6. If role !== 'judge', signs out and shows error: "This account is not registered as a judge."
  7. On success, navigates to /judges/results
  8. JudgesRoute guard verifies session + role on every access

Result Re-Verification Flow (Judge Editing Locked Results)

  1. Judge clicks "Re-verify & Edit" on a locked result
  2. Prompt: "Are you really a Judge?"
  3. CAPTCHA challenge generated via judge_create_captcha RPC (6-char code, 5-minute expiry)
  4. Judge re-enters email + password
  5. Enters the CAPTCHA code
  6. Client calls judge_reverify_edit RPC with all data
  7. Server-side verification: checks JWT role, validates password via crypt(), validates CAPTCHA (valid, unexpired, unused)
  8. On success: upserts result, sets locked=true, writes audit log to result_edit_log

Admin Panel — Features & Workflows

Dashboard (/admin)

Displays live statistics (total participants, teams, categories, programmes via row counts), a team points leaderboard sorted by total points across all published results, and individual points leaderboard by student category (Minor, HS, Premier, Sub Junior, Junior) with per-category tabs.

Programme Management (/admin/programmes)

Capabilities

  • Add/Edit/Delete programmes with fields: name, category, programmeType (On-stage/Off-stage), participationType (Individual/Group), result number
  • Toggle publish status (isPublished) — controls public result visibility
  • Clear result — resets placements, marks as not finished
  • Bulk import from CSV/Excel/PDF/OCR via ProgrammeBulkImportModal
  • Filter by category, programme type, participation type
  • Paginate (25/50/100/200/All)
  • View enrolled participants modal per programme

Workflow: Creating a Programme

  1. Click "Add Programme"
  2. Enter name, select category, programme type, participation type
  3. Optionally assign result number (or auto-assign)
  4. Save — placeholder result row is auto-created via ensureResultMasterRow()
  5. Programme appears in admin list and (if published) in public results

Workflow: Publishing Results

  1. Judge submits result (locked + has data) via /judges/results
  2. Admin reviews in /admin/results (read-only preview)
  3. Admin toggles "Published" on the programme in /admin/programmes
  4. Result becomes visible on /results and /results/:id
  5. Student sees result on their dashboard

Team Management (/admin/teams)

View team scores (auto-calculated from published results via sync_team_totals trigger). Edit team name and color (16 preset colors). Expandable TeamBreakdown component shows per-category point breakdown and placement details.

Participant Management (/admin/students)

Capabilities

  • Add/Edit/Delete participants with fields: name, chest number, category, team, photo, programme enrollment
  • Photo upload to Supabase Storage (students/ folder)
  • Bulk import via BulkImportModal (CSV/Excel/PDF/OCR)
  • Filter by team and category
  • View enrolled programmes modal

Category Management (/admin/categories)

CRUD for the categories table. Controls which categories appear in dropdowns/filters across the app. Default seed data: Minor(1), HS(2), Premier(3), Sub Junior(4), Junior(5), General Cat-A(6), General Cat-B(7).

Results Viewer (/admin/results)

Read-only results preview. Programme-centric list: every programme gets a row with result data. Shows placement rows (1st/2nd/3rd) with chest number, name, team, points, grade. Search by name/result number. Status badges: Published / Awaiting Publish / No result.

Gallery Management (/admin/spotlight)

Upload images (up to 10 per batch) to Supabase Storage. Add captions, assign to albums. Toggle "Hero banner" status (appears in home hero carousel). Edit caption/album. Delete images.

Gallery Footer Management (/admin/frames/footer)

Upload transparent PNG frames. Create/Edit/Delete footer overlays. Set one as "active" — enforced by trigger to ensure at most one active footer. Active footer is composited onto gallery photos at display time.

06 — Student Panel — Features & Workflows

Student Panel — Features & Workflows

Login (/student/login)

Students authenticate with chest number + password. The system uses a custom session mechanism (not Supabase Auth) with the following properties:

  • Credentials checked against student_credentials table, with fallback to common password israfest2026
  • Session stored in both localStorage and the students table (dual storage)
  • 8-hour session expiry
  • Single-device enforcement: if sessionActive=true in DB, login is rejected with 'already_logged_in_elsewhere'

Dashboard (/student/dashboard)

Profile Display

  • Student name, chest number, category, team
  • Profile photo (or colored initial avatar fallback)
  • Circular progress ring showing completed/total programmes

Programme Lists

  • Completed: Programmes where the student has a placement in published results
  • Pending: Enrolled programmes without results yet

Poster Download

  1. Student clicks "Download Poster" button
  2. Picker modal shows completed programmes
  3. Selects a programme → opens TemplatePosterModal (if templates exist) or ResultPoster (3-theme fallback)
  4. Downloads poster as PNG

Edit Details (Admin-Gated)

Students can self-edit their profile, but must first authenticate an admin session:

  1. Student clicks "Edit Details"
  2. Prompted for admin email + password
  3. System calls supabase.auth.signInWithPassword() with admin credentials
  4. On success, edit form opens with fields: photo, name, category, team, programme enrollment
  5. Changes saved via Supabase client (now authenticated as admin)
  6. Admin session signed out after edit closes
Why? Students operate as the anon role in Supabase. RLS policies on the students table require authenticated role for writes. The admin re-authentication provides the necessary credentials.

Logout

Clears both localStorage session and DB session state (sessionActive=false), then redirects to /student/login.

07 — Judge Panel — Features & Workflows

Login (/judges/login)

Uses the isolated judgeClient instance. Validates app_metadata.role === 'judge' after sign-in. Clears any existing session before new login.

Result Entry Panel (/judges/results)

Layout

  • Category filter dropdown
  • "Not Submitted" section: programmes awaiting results
  • "Submitted Results" section: locked results (read-only unless re-verified)

Workflow: First-Time Result Entry

  1. Judge selects a programme from "Not Submitted" list
  2. Clicks "Enter Result" to open the editor
  3. Editor shows code letter dropdowns (populated from performance_code_assignments table)
  4. Selects code letters and enters points (0-10) for each placement
  5. Grade auto-calculated: 10=A+, 8-9=A, 6-7=B, 4-5=C
  6. Can add multiple entries (dynamic row count)
  7. Clicks "Save & Lock Result"
  8. Result row updated with locked: true, isFinished: true
  9. Programme moves to "Submitted Results" section

Workflow: Editing Locked Results (Re-Verification)

  1. Judge clicks "Re-verify & Edit" on a locked result
  2. Passes through re-verification flow (CAPTCHA + email + password)
  3. Server-side verification via judge_reverify_edit RPC
  4. Editor opens with existing entries pre-filled
  5. Judge makes changes and saves
  6. Audit log written to result_edit_log table

09 — Green Room & Lot Draw System

Access Gate (/lots)

PIN-protected access (hardcoded 6-digit code: 201219). On success, sets sessionStorage('lots_granted'). No Supabase authentication involved.

Lot Draw (/lots/draw)

Three operational modes:

Mode 1: Topic Lotting

  • Generates N numbered cards (1 to N)
  • Shuffle and flip to reveal entry order numbers
  • 3D CSS card-flip animation
  • Max 60 cards

Mode 2: Code Letter Lotting

  • Generates N lettered cards (A to Nth letter)
  • Max 26 letters
  • Same card-flip animation

Mode 3: Code Assignment (Green Room)

  1. Select Category from dropdown
  2. Select Programme from dropdown
  3. View enrolled candidates with code letter dropdowns
  4. Assign unique code letters (A, B, C...) to each candidate
  5. Save → upserts to performance_code_assignments table with conflict resolution on (programme_id, code_letter)

This system enables blind grading — judges see only code letters, not student names.

Poster Generation System

Architecture

The poster system consists of four layers:

LayerFile(s)Responsibility
Data Modelsrc/utils/posterTemplates.jsTemplate definitions, field mappings, data resolution, storage
Renderingsrc/components/PosterStage.jsxInteractive canvas with drag, resize, rotation, grid, snap guides

Template Model

  • Canvas: 1080×1080 (standard 1:1) or legacy 720×960
  • Types: result (programme winners) and standings (team leaderboard)
  • Elements: Positioned text layers with optional data field bindings
  • Repeatable fields: {i} placeholder renders multiple rows (one per placement/team)
  • Backgrounds: Solid color, gradient (9 presets), or uploaded image

Poster Export Workflow

  1. Admin designs template in AdminPosterEditor (or uses default)
  2. Template saved to poster_templates table (with localStorage fallback)
  3. User clicks "Export Poster" in editor OR "View Posters" on public result page
  4. buildPosterSource() creates a value map from live programme/result data
  5. PosterStage renders template with real data injected into field bindings
  6. html2canvas captures the rendered DOM at 2x scale
  7. file-saver triggers PNG download

Cumulative Team Poster (AdminResultPoster)

  1. Admin enters programme count (multiples of 5)
  2. System sums points per team across first N published programmes
  3. Renders a green gradient poster with team rankings
  4. Captures via html2canvas, stores in localStorage
  5. Admin can toggle publish/unpublish for student download area

Legacy Poster System (ResultPoster)

Fallback when no templates exist. Renders 3 poster variants (Classic, Vibrant, Minimal) with programme name, result number, 1st/2nd/3rd winners, and points. Each captured via html2canvas at 2x scale.
